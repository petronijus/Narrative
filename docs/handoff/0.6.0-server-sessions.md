# 0.6.0 — Server-driven session cookies — deploy notes

Cutover from the browser-PKCE flow (Google `id_token` in `localStorage`,
hidden-iframe silent renew) to a server-driven OAuth + opaque session
cookie flow. Sessions now last 30 days sliding and work in every
browser identically.

## Before pushing the redeploy

### 1) Google Cloud Console

OAuth client → Credentials → "Web application" → **Authorized redirect URIs**.

Add:

- `https://narrative.example.com/api/auth/callback` (prod — Caddy strips `/api/` before forwarding)
- `http://localhost:3001/auth/callback` (local dev — the SPA navigates directly to the server origin)

Keep (only briefly — remove once prod redeploys):

- `https://narrative.example.com/auth/callback` (old browser-PKCE redirect)

### 2) Generate + add `SESSION_COOKIE_SECRET` on the VM

```bash
ssh petr@192.0.2.147 'openssl rand -hex 32'
# → append to /home/user/narrative/infra/.env.prod:
#   SESSION_COOKIE_SECRET=<that-hex>
```

This signs the short-lived (10 min) PKCE state cookie. Without it the
server throws on boot (`SESSION_COOKIE_SECRET must be set in
production`).

### 3) Confirm `OIDC_CLIENT_SECRET` is already there

It was added in 0.5.x. Sanity-check it's still in `.env.prod`:

```bash
ssh petr@192.0.2.147 'grep -c OIDC_CLIENT_SECRET= /home/user/narrative/infra/.env.prod'
# → 1
```

## Redeploy

Same flow as 0.5.x (no infra changes beyond env). The new migration
(`0012_sessions.sql`) runs automatically.

```bash
# rsync local repo to the VM (skip node_modules / dist / .env.prod / .git)
rsync -avz --delete \
  --exclude node_modules --exclude dist --exclude .git \
  --exclude .env --exclude infra/.env.prod \
  ./ petr@192.0.2.147:/home/user/narrative/

# deploy
ssh petr@192.0.2.147 '
  cd /home/user/narrative &&
  USE_SHARED_TUNNEL=1 ./infra/scripts/deploy.sh prod
'
```

## What to verify after redeploy

1. `https://narrative.example.com/` → unauthenticated → redirect to
   `/auth/login`.
2. Click "Sign in with Google" → Google consent → land back on `/`
   immediately (no `/auth/callback` page render — server 302s
   straight through).
3. DevTools → Application → Cookies for `narrative.example.com`:
   `narrative_session` present, HttpOnly ✓, Secure ✓, SameSite=Lax,
   Path=/, expires in ~30 days.
4. DevTools → Application → Storage → Local Storage: no
   `oidc.user:*` entry any more.
5. Network tab: every API call carries `Cookie: narrative_session=…`
   instead of `Authorization: Bearer eyJ…`.
6. Network tab → WS upgrade for `/ws`: same cookie on the upgrade
   request. Status 101.
7. Make an edit, close the browser entirely, reopen `https://narrative.example.com/` 5+ min later — should land directly on the deck list without a login prompt.
8. POST `/api/auth/logout` (or click the logout chip when it lands) → cookie cleared → bounce to `/auth/login`.

## Rollback

If the deploy goes sideways:

```bash
ssh petr@192.0.2.147 '
  cd /home/user/narrative &&
  git checkout v0.5.1 &&
  USE_SHARED_TUNNEL=1 ./infra/scripts/deploy.sh prod
'
```

The `0012_sessions.sql` migration only adds a new table; rolling back
to 0.5.1 doesn't require dropping it — the column-less schema is
forward-compatible. (If you do want to drop the table:
`DROP TABLE sessions CASCADE;` in the prod Postgres.)

## Architectural note for future readers

If a future session asks "why is the SPA's AuthContext so thin?" — this
is by design. The browser only holds:

- An opaque session id in an HttpOnly cookie it can't read.
- A `{ sub, email, name }` shape derived from a single `/auth/me`
  request on mount.

Everything else (token validation, refresh, revocation, allowlist
enforcement) lives server-side. The 30-day sliding expiry on
`sessions.expires_at` means the only re-login triggers are:

- Explicit logout (POST `/auth/logout`).
- 30 days of inactivity.
- Server-side `revokeAllSessionsForUser(...)` (allowlist revoke,
  password reset etc. — not exposed via API yet).
