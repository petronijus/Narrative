# 0.7.1 — Invite emails via Resend

Sends the actual "you've been invited" email when a Narrative deck owner
adds a collaborator by email. Closes the 0.7.0 follow-up.

## What's new

- `apps/server/src/email/client.ts` — Resend SDK wrapper with a dev/no-key
  fallback (logs to stdout instead of throwing).
- `apps/server/src/email/templates/deckInvite.ts` — HTML + plaintext
  template, inlined styles, includes deck title, inviter name, role, and
  a sign-in URL that lands the recipient directly on the right deck after
  authentication.
- `POST /decks/:id/permissions` (pending-invite branch) fires the email
  fire-and-forget after writing the DB row. Database row remains the
  source of truth; email failure never blocks the invite.
- Env vars: `RESEND_API_KEY`, `EMAIL_FROM`. Both optional — without them
  the system continues working, just without delivery.

## Setup before deploy

### 1) Resend account

1. Sign up at https://resend.com (free tier: 100 emails/day, 3 000/month).
2. **API Keys** → "Create API Key" → copy the `re_...` value.

### 2) Verify the example.com domain in Resend

Required to send FROM `*@example.com`. Without verification you can only
send TO the email of your Resend account owner — fine for the first
smoke test but blocks real invites.

1. Resend dashboard → **Domains** → "Add Domain" → `example.com` → pick
   region (EU recommended for GDPR).
2. Resend shows three DNS records — copy each one:
   - **MX** on `send.example.com` → `feedback-smtp.eu-west-1.amazonses.com` (priority 10)
   - **TXT** on `send.example.com` → SPF: `v=spf1 include:amazonses.com ~all`
   - **TXT** on `resend._domainkey.example.com` → DKIM public key (~ 400 chars)
3. In Cloudflare DNS for `example.com`:
   - MX records: add as-is.
   - TXT records: add as-is. Cloudflare may auto-flatten the DKIM TXT —
     that's fine.
   - **Proxy status**: DNS only (gray cloud) for all three.
4. Back in Resend → click "Verify". Usually green within ~30 s; can take
   up to a few hours if Cloudflare TTL is high.

### 3) (Optional) DMARC

Adds policy + reporting on top of SPF/DKIM. Recommended:

```
TXT on _dmarc.example.com → "v=DMARC1; p=none; rua=mailto:dmarc@example.com"
```

`p=none` = monitor only. Once you see reports for a week and everything's
aligned, move to `p=quarantine` or `p=reject`.

### 4) Set env vars on the VM

```bash
ssh petr@192.0.2.147
sudo nano /opt/narrative/infra/.env.prod
```

Add (or update) at the bottom:

```
RESEND_API_KEY=re_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
EMAIL_FROM=Narrative <noreply@example.com>
```

Save + exit.

### 5) Deploy

```bash
ssh petr@192.0.2.147 'cd /opt/narrative && USE_SHARED_TUNNEL=1 ./infra/scripts/deploy.sh prod'
```

Only the server container restarts; other services keep running.

## Verify after deploy

### Smoke test (no DNS verification needed yet)

1. Set `EMAIL_FROM=Narrative <onboarding@resend.dev>` (Resend's shared dev
   sender) in `.env.prod` instead of a `@example.com` address.
2. Invite **your own** Resend-account email (the one you signed up with).
3. Check that mailbox — invite should arrive within seconds.

### Full test (after domain verification)

1. Invite a real collaborator's email from the Share dialog.
2. They receive the email titled `Jane Doe invited you to "..." on Narrative`.
3. Clicking "Open the deck" sends them through Google sign-in, then drops
   them straight onto `/deck/<id>` — `consumePendingInvitesForEmail()`
   runs during `/auth/callback`, converts the pending invite to a
   permission, and the deck is in their list.
4. Check `docker logs narrative-server` for the line
   `[email] resend rejected` or `[email] send threw` — neither should
   appear on a healthy send.

### Behaviour when RESEND_API_KEY is missing

`docker logs narrative-server | grep '\[email\]'` shows:

```
[email] RESEND_API_KEY missing — would-be email: { to: 'invitee@…', subject: '…', text: '…' }
```

The pending invite row is still created; the dialog still shows it; the
flow still works if the operator tells the invitee out-of-band to log in.
This is the safe fallback for the period between deploy and DNS
verification finishing.

## Rollback

The email send is fire-and-forget and never blocks the invite create
path, so rollback is purely "code-level" — no schema, no env-var
dependency.

```bash
ssh petr@192.0.2.147 '
  cd /opt/narrative && git checkout v0.7.0 &&
  USE_SHARED_TUNNEL=1 ./infra/scripts/deploy.sh prod
'
```
