## Still open

### R1 — slide 5 radial-gradient ellipses render solid blue in the editor

The slide's two corner ellipses parse correctly:

```json
{
  "type": "ellipse",
  "fill": 16777215, // 0xFFFFFF (set by writer.ts pickFillForShape)
  "fillStyle": {
    "kind": "radialGradient",
    "stops": [
      { "offset": 0.049, "color": 0 }, // black
      { "offset": 0.217, "color": 16579837 }, // #FCFCFD near-white
      { "offset": 0.697, "color": 16579837 },
      { "offset": 0.994, "color": 16579837 }
    ],
    "centerX": 0.5,
    "centerY": 0.5
  }
}
```

The Y.Doc is correct (verified via
`apps/server/src/scripts/dumpDeck.mjs <deckId>`). In present mode the
slide renders as **uniform blue** — no visible gradient transition,
no near-white outer ring, no black center. As if the gradient texture
isn't being applied at all and Pixi is falling back to a different
solid color.

Suspected fault paths to investigate (in order):

1. `apps/web/src/renderer/objectRenderers/ellipseRenderer.ts:60`
   `drawEllipse` calls `fillStyleToPixi` → returns
   `resolved.input = { texture }` → `graphics.fill({ texture })`.
   In Pixi v8, `Graphics.fill({ texture })` may default `color` to
   something non-white that tints the texture.
2. `apps/web/src/renderer/fillStyleToPixi.ts:208` `paintRadialGradientTexture`
   creates the canvas + gradient + `Texture.from({ resource: canvas })`.
   Verify the texture has correct bytes (not an empty / black texture).
3. `acquireOrPaint` ref-counted procedural cache — if it returns a
   stale texture from a different shape, two ellipses sharing a key
   could collide.

Reproduce: import the fixture
`tests/fixtures/pptx/sample-deck.pptx`, open the
deck, navigate to slide 5. Compare against
`tests/fixtures/pptx/reference/sample-deck/Slide5.png`.

### R2 — video poster covered by "processing" placeholder

Slide 7's video shape has an HLS-pending `transcodeStatus`. The
`pptx/writer.ts` now emits a sibling `ImageObject` (the blipFill
poster) before each `VideoObject` at the same bbox so the slide
stays visible. The image **is** in the Y.Doc:

```text
slide 7: 13 objects
  [0] type=image  assetId=...  bbox=(0,0.28 1919×1079)   ← poster
  [1] type=video  assetId=...  bbox=(0,0.28 1919×1079)
  ...
```

But the slide renders blank because
`apps/web/src/renderer/objectRenderers/videoRenderer.ts:556`
`applyVideoInfoResult` paints an opaque grey loading placeholder + a
"processing" label on top of every video whose
`transcodeStatus: pending`. Both occlude the underlying poster image.

Options:

- Make the loading placeholder transparent when the renderer detects
  another object at the same bbox underneath (intrusive — the renderer
  doesn't know about scene-graph siblings).
- Skip the placeholder entirely in present mode (`useRenderMode === 'present'`)
  and rely on the underlying poster image. The "processing" label is
  more useful in the editor than in front of an audience.
- Wire the poster blipFill into the VideoObject schema (e.g.
  `posterAssetId?: string`) and have the video renderer load that
  texture instead of waiting for HLS.

The third option is the cleanest but requires schema work on the
slide-model package and matching write logic in
`apps/server/src/pptx/importDeck.ts` (which currently emits the
poster as a separate `ImageObject`, not as video metadata).

### F1 — custom font import from the PPTX

The fixture uses `Northwind Sans ST Pro 36 Bold`, `Asterisk Sans
Variable Black`, and `Druk` family — none of which are uploaded into
the deck's font registry. Knock-on effects with secondary visible
symptoms:

- Titles "Soul" / "System" / "Change?" / "DAWN OF DESIGN" render as a
  generic serif fallback.
- Subtitle / author wraps differ because the fallback's metrics are
  wider — slide 1's "Jordan Example — Head of icon incar Prague" line
  clips off the bottom of the text box.
- Slide 2's "DESIGN" (in "DAWN OF DESIGN") sinks below the visible
  area for the same reason — the text box was sized for the original
  font's tighter advance.

The current import pipeline doesn't walk `ppt/fonts/*.ttf` inside
the .pptx zip. Sketch:

1. Extend `parser.ts:embeddedImages` to also surface font entries.
2. Extend `importDeck.ts:uploadEmbeddedImagesAndPatchAssetIds` to
   upload font files under `decks/<deckId>/fonts/<assetId>/original.ttf`
   with `kind='font'`.
3. Probe `name` table via `opentype.js` (already a server dep) to
   populate `fontFamily` / `fontWeight` / `fontStyle` / `postscriptName`
   on the `media_assets` row.
4. Trigger the deck's font registry to load them on open (P15 pipeline
   already exists for user-uploaded fonts; this just wires up a
   different source).

Scope: large. Probably warrants its own milestone (M30 or P15 phase 2).
