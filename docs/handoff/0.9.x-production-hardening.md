# 0.9.0 → 0.9.3 — Production hardening (2026-09-07 → 2026-09-09)

**Status**: shipped and deployed. Production runs `v0.9.3` plus two
config-only fixes merged after the tag (PRs #72, #73).
**Last commit**: `f916575` (merge of PR #73, 2026-09-09).
**Tags**: `v0.9.0` (2026-09-07), `v0.9.1` (2026-09-08), `v0.9.2` (2026-09-09),
`v0.9.3` (2026-09-09).
**Deployed**: `curl -s https://narrative.bastla.com/version.json` →
`{"version":"v0.9.3+00454ec"}` (checked 2026-09-09).

This is the record of two sessions that fixed ten production defects. Nine of
the ten were **invisible in `pnpm dev`** — they existed only behind Cloudflare
Tunnel, only under the production CSP, or only in a browser that had cached
something. The single most useful lesson of the arc is at the bottom, under
_Why dev never saw any of this_.

---

## Session 1 (2026-09-07) — five production-only defects, one release

Released as **0.9.0**, the first tagged release since 0.8.1. It carries
everything merged in between (multi-level lists, the .pptx import/export work,
the public-release prep, the move to GHCR-built images) plus the five fixes
below. Full change set: `git log 0.8.1..v0.9.0`.

### 1. `415 FST_ERR_CTP_INVALID_MEDIA_TYPE` on every upload and on logout

Cloudflare Tunnel re-frames a bodyless POST — one sent with
`Content-Length: 0` — as `Transfer-Encoding: chunked`. Fastify's `isEmptyBody`
check keys off `Content-Length`, so it no longer recognises the body as empty,
looks for a parser matching the (absent) `Content-Type`, finds none, and
answers **415 before any route or hook runs**. Nothing in the application code
was reached, which is why the server logs showed nothing interesting.

Fix: a `'*'` fallback content-type parser in
`apps/server/src/http/bodylessCompat.ts` that accepts a genuinely empty body
and still returns 415 for a real unsupported payload. Commit `fcfa28a`,
cherry-picked onto `main` as `5da133b`.

### 2. tus uploads died on the first HEAD with `[object ProgressEvent]`

Caddy rewrites `Host` to the upstream hostport, and `handle_path /api/*` strips
the prefix before proxying. tus built its `Location` from what it saw and
answered `Location: http://server:3001/api/uploads/<id>` — a Docker-internal
hostname, and one path segment short of the public URL. Commit `6ce04d2`.

### 3. …and fixing the host was not enough

Caddy overwrites `X-Forwarded-Proto` with `http`, because the tunnel terminates
TLS at the edge and speaks plain HTTP to Caddy. So the corrected absolute URL
was `http://` on an `https://` page — mixed content, blocked by the browser.

Final answer: **tus returns a relative Location**, which settles scheme and
host by construction (the browser resolves against the origin it is already
on). The only thing the upstream genuinely cannot know is the prefix the proxy
stripped, and that arrives as `X-Forwarded-Prefix`. See
`buildPublicUploadUrl()` in `apps/server/src/media/tus.ts`, commit `cd6a52a`.

### 4. Imported decks rendered nothing

Pixi v8 generates shader code with `new Function`. The production CSP is
`script-src 'self'` with no `'unsafe-eval'`, so `app.init()` threw and the
renderer never started at all.

Fixed with Pixi's own eval-free polyfill (`import 'pixi.js/unsafe-eval'`)
rather than loosening the policy. Commit `9acfa15`.

### 5. Text rendered but images never did

`worker-src 'none'` killed the Worker that Pixi decodes textures in, so
`Assets.load()` never settled — no error, just a promise that never resolved.
Slide thumbnails use a **different** path (`Image.decode()` directly) and kept
working, which masked the failure and sent the first round of diagnosis toward
the wrong layer. Now `worker-src 'self' blob:`. Commit `2605aba`.

Separately in the same commit: a hand-written `-webkit-backdrop-filter` made
Lightning CSS drop the **standard** `backdrop-filter` from the minified build,
so the backdrop blur under the side panels existed in dev and vanished in
production.

### 6. Deploys looked like they did nothing

`index.html` was served with **no** `Cache-Control` header at all, so browsers
applied heuristic freshness off `Last-Modified` and kept serving the previous
document — and therefore the previous bundle — until a hard reload. Now served
`no-cache`. This is the root of the 0.9.3 work below; the header fixed the
future, not the browsers that had already cached a document without it.

### Also in session 1

- **GitHub Actions removed entirely** (commit `573ba64`), at the user's
  request. Both workflows had been failing since 2026-06-17 on a pnpm version
  conflict. Checks run locally per `CLAUDE.md`: `pnpm typecheck`, `pnpm lint`,
  `pnpm -r test`. There is no `.github/` directory in the repo any more.
- **Release discipline established.** Versions 0.9.0 → 0.9.3, a CHANGELOG
  section per version, git tags, and the invariant **git tag = package version
  = deployed image tag**.
- **Production moved off hand-built images** to the GHCR pipeline:
  `infra/scripts/build-push.sh` builds locally and pushes
  `ghcr.io/petronijus/narrative-{server,video-worker,web}`;
  `infra/scripts/deploy.sh` on the VM only pulls.

## Session 2 (2026-09-08 → 2026-09-09) — three releases and two config fixes

### 0.9.1 — .pptx import lost fonts and text

Measured on a real deck: **699 of 955 runs (73 %) arrived with no
`fontFamily`**, and the slide-1 title was invisible. Two causes, both in
`apps/server/src/pptx/parser.ts` (commit `42d2fc6`, PR #69):

1. **Placeholder inheritance replaced instead of merged.** The layout's entry
   overwrote the master's _wholesale_, so a layout placeholder without
   `<a:xfrm>` shadowed the master's box and the frame came out `0×0`. The
   renderer then word-wrapped at width 0 — one glyph per line, measured
   **4704 px tall on a 720 px slide** — and the clip mask removed what was
   left. Geometry now merges per field, gated by a `hasGeometry` flag.
2. **Theme font references were skipped outright.** OOXML names a template's
   fonts indirectly (`<a:latin typeface="+mn-lt"/>`), and the parser had a code
   comment admitting there was no font-scheme resolver. `theme1.xml`'s
   `<a:fontScheme>` is now parsed and `+mj-*` / `+mn-*` resolved; fonts inherit
   the full chain **run → shape → placeholder → master `<p:txStyles>` →
   theme**.

After: **955 runs with a font, 0 without, 0 unresolved theme references**, and
the slide-1 title back at 1213×606. 5 new regression tests in
`apps/server/src/pptx/parser.test.ts`.

### 0.9.2 — a deck could open to a blank canvas until the page was reloaded

Pixi runs with `autoStart: false`. The first paint is a synchronous
`renderNow()`; everything after it — including the deck's own objects, which
arrive over the WebSocket _after_ init — goes through `markDirty()` and a rAF.
A page that is not visible gets no animation frames, so that frame stays
pending forever, and `markDirty()` early-returns while one is pending. The
visibility handler therefore did nothing at exactly the moment a repaint was
due.

It now calls `renderNow()`, which cancels the stalled frame and paints
synchronously, and also repaints on a bfcache restore (`pageshow` with
`persisted`), where Pixi never re-initialises and so never gets a first paint
at all. First tests for `RenderScheduler` (3, in
`apps/web/src/renderer/RenderScheduler.test.ts`). Commit `c4b0b21`, PR #70.

> ⚠️ **The original report was never reproduced.** A background page in
> headless Chrome still reports `visibilityState: "visible"`, so the probe
> could not create the condition. This is a real defect that matches the
> reported symptom — it is **not** a confirmed cause. If a blank canvas is
> reported again, do not assume this closed it.

### 0.9.3 — version guard

A browser that cached `index.html` **before** the `no-cache` header existed
keeps serving a months-old copy for weeks: heuristic freshness is roughly 10 %
of the document's age off `Last-Modified`, so an old document gets _more_
patient, not less. Production hit exactly that on 2026-09-09 — a June document
pulling June chunks.

The build now stamps its version into `/version.json` as well as into the
bundle, and `apps/web/src/state/versionGuard.ts` compares the two at startup
and on tab focus. On a mismatch it reloads via
`fetch(location.href, { cache: 'reload' })` first — a plain `location.reload()`
would re-serve the stale cache entry — then `location.reload()`.

Deliberately conservative: an **unreadable** version never triggers a reload
(an offline moment or a proxy pinned to an old document must not cost anyone
unsaved work), and each served version reloads **at most once per tab**.

Two supporting fixes without which the guard would have misfired:

- `vite.config.ts` resolved the build version **twice** (once for the
  `__BUILD_VERSION__` define, once for the new asset). Two independent calls
  can disagree — which would have reloaded every client exactly once.
- Docker builds have no `.git`, so the resolver fell back to `v<pkg>+build`,
  identical for every build of a version. `build-push.sh` now passes the real
  tag + short sha via `VITE_BUILD_VERSION`.

Commit `107cc20`, PR #71.

### CSP too tight for the renderer (deployed 2026-09-09, config-only, no release)

Two more CSP directives were blocking Pixi. Commit `931e648`, PR #72:

- **`font-src 'self'` blocked Pixi's HTMLText font embedding.** Pixi builds an
  SVG whose `@font-face` embeds the font as a **data URL** — see
  `pixi.js/lib/scene/text-html/utils/loadFontCSS.mjs`, `src: url('${dataSrc}')`.
  With `data:` disallowed, **every canvas text fell back to a system face,
  regardless of the deck**. This is the render-side half of the font problem
  and is entirely independent of the 0.9.1 parser fix: a correctly imported
  font still rendered wrong.
- **`connect-src 'self'` blocked Pixi's ImageBitmap probe.** `checkImageBitmap`
  fetches a 1×1 `data:` PNG inside the texture worker; the fetch was refused
  and it threw on every texture load.

Both directives now allow `data:`. Verified live on 2026-09-09:

```
$ curl -sI https://narrative.bastla.com/ | grep -i content-security-policy
content-security-policy: default-src 'self'; script-src 'self';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
  media-src 'self'; font-src 'self' data:; connect-src 'self' data:;
  worker-src 'self' blob:; object-src 'none'; base-uri 'self';
  frame-ancestors 'none'; frame-src 'none'
```

### Caddy config was mounted as a single file (PR #73)

The trap that cost the most time per line of fix in the whole arc. Compose
mounted `./caddy/Caddyfile:/etc/caddy/Caddyfile`. **A single-file bind mount is
pinned to the file's inode**, and the deploy syncs config in with rsync, which
_replaces_ files rather than rewriting them in place. The container therefore
kept reading the old, unlinked inode while:

- the file on the host showed the new config,
- `caddy validate` passed,
- `caddy reload` reported success,
- and the served headers were still the previous ones.

Every direct signal said the change had landed. Only `curl -sI` against the
public URL disagreed. Fixed by mounting the **directory** (`./caddy:/etc/caddy:ro`),
commit `e6b4042`. The reasoning is written into
`infra/docker-compose.prod.yml` beside the mount so it cannot be undone by
accident.

## Why dev never saw any of this

Every defect in this arc lived in one of four gaps between `pnpm dev` and
production. Worth internalising, because the next production bug will be in
one of them too:

| Gap                          | What only exists in prod                                                                 | Bit us in                                                              |
| ---------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **The tunnel**               | Cloudflare re-frames requests; TLS terminates at the edge and the origin sees plain HTTP | 415 on bodyless POST; tus mixed-content Location                       |
| **The proxy**                | Caddy rewrites `Host`, strips `/api` via `handle_path`, overwrites `X-Forwarded-Proto`   | tus Location (both rounds)                                             |
| **The CSP**                  | Vite's dev server sends no CSP at all                                                    | Pixi `new Function`; texture worker; HTMLText fonts; ImageBitmap probe |
| **The minifier + the cache** | Lightning CSS only runs on a prod build; browsers only cache what a server told them to  | backdrop-filter; stale `index.html` for weeks                          |

Corollary for the CSP specifically: **a CSP denial is often silent**. A blocked
worker yields a promise that never settles; a blocked font yields a silent
fallback face. Do not expect an exception. When the renderer misbehaves in
production and not in dev, read the live CSP header first.

## Known-open — this is the next-step list

### 1. Text jumps when zooming, and alignment shifts (diagnosed, NOT fixed)

`applyVerticalAlign` / `applyHorizontalAlign` in
`apps/web/src/renderer/objectRenderers/textRenderer.ts` compute the block
offset from a **snapshot** of the measured size:

- vertical: `textNode.y = data.height − textNode.height` (bottom) or half that
  (middle);
- horizontal: via `anchor.x` + `x` against `data.width`.

Neither refresh path re-runs them. `SceneGraph.forceTextResolutionRefresh()`
(zoom-driven resolution change) and `SceneGraph.refreshTextNodesUsingFamily()`
(font load) only reset the GPU cache key and mark the texture dirty. So when
metrics change under a re-rasterisation — **the font arriving is the big
one** — the block keeps a stale offset and visibly jumps.

Evidence from the real deck, slide 3:

| Object     | model height | measured | `textY` |
| ---------- | ------------ | -------- | ------- |
| `HIbkfrux` | 331.21       | 159      | 172.2   |
| `YhA4hJsE` | 356.60       | 159      | 197.6   |

Measured **non-causes**, so nobody re-derives them:

- Node geometry does **not** drift across a zoom — all deltas measured 0.
- A pure resolution change moves glyph rasters by **0.12 % of pixels**, edges
  only. The jump is not rasterisation noise.

Starting point: the diagnostic spec
`apps/web/e2e/zoom-text-probe.spec.ts` (measures fonts, model-vs-measured
geometry and screenshots across a resolution change, driven by
`PROBE_DECK_ID` / `PROBE_SLIDE`). Likely shape of the fix: have both refresh
paths re-run the two align functions after the re-rasterisation settles,
rather than only invalidating the texture.

### 2. Scrollbar in the slides panel jumps while a deck loads (NOT reproduced)

Reported on production; the local probe could not reproduce it. On a 47-slide
deck, `scrollTop` stayed constant at 0 for 20 s, `scrollHeight` was constant,
and all 47 items were present from the first sample.

Suspicion: it was a symptom of the CSP problem above — a texture-load exception
on every image. **Re-check now that `connect-src`/`font-src` allow `data:`**
before spending more time on it.

### 3. Cloudflare injects a script the repo does not contain

Downstream of Caddy, Cloudflare adds an inline script plus
`static.cloudflareinsights.com/beacon.min.js`. The `index.html` on disk carries
neither. It is **left blocked deliberately** — the CSP does its job and the
console reports it. Silencing it means one of:

- turn off Web Analytics in the Cloudflare dashboard (**recommended**), or
- allow `'unsafe-inline'` in `script-src` for a third-party beacon (not worth
  it).

### 4. Playwright cannot install its bundled browsers on Ubuntu 26.04

```
$ npx playwright install chromium
Failed to install browsers
Error: ERROR: Playwright does not support chromium on ubuntu26.04-x64
```

Same for the ffmpeg download, which is what video capture needs. Verified on
`petronijus-PC` (Ubuntu 26.04.1 LTS) on 2026-09-09; `~/.cache/ms-playwright`
does not exist, so **the plain `pnpm --filter web test:e2e` fails on this
machine**.

**The escape hatch already exists in `apps/web/playwright.config.ts`** — it was
added for exactly this, and is easy to miss:

```bash
PLAYWRIGHT_USE_SYSTEM_CHROME=1 PLAYWRIGHT_NO_VIDEO=1 pnpm --filter web test:e2e
# or point at a specific binary:
PLAYWRIGHT_CHROME_EXECUTABLE=/usr/bin/google-chrome PLAYWRIGHT_NO_VIDEO=1 …
```

`PLAYWRIGHT_USE_SYSTEM_CHROME=1` selects `channel: 'chrome'`
(`/usr/bin/google-chrome` is installed here) and `PLAYWRIGHT_NO_VIDEO=1` turns
off video capture. The 0.9.x diagnostic probes pinned the same two settings
per-spec instead (`test.use({ channel: 'chrome', video: 'off' })`).

So the accurate statement is: **the suite runs on this machine only with those
env vars set**. Whether it passes with them set was not measured during this
arc — do not claim it either way without running it. The durable options are to
make those the defaults when the bundled browser is absent, or to run the suite
in a container with a supported base image.

### 5. Deployment drift — resolved, with one caveat

Production runs a tagged GHCR image again. The caveat to keep in mind:
**`/opt/narrative` on the VM is an rsync of the working tree, not a git
checkout** — there is no `git pull` there, and `git log` on the VM means
nothing. The images are the versioned artifact; the directory is only config +
scripts.
